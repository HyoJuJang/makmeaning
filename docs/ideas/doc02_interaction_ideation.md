# GS SHOP — Interaction을 뒤집는 두 번째 아이데이션

작성일: 2026-09-21 · 이전 문서: `doc01_research_ideation.md` · 대응 HTML: `doc04_top3_ideation.html`

## 이번 라운드의 범위

문제 탐색은 이전 라운드의 결과를 유지했다. GS SHOP을 새로 조사하거나 새로운 고객 문제를 발견했다고 주장하지 않는다. 같은 근거 위에서 해결 방식과 고객의 행동을 발산했다. 아래 UI는 새 제품의 컨셉이며 현재 GS SHOP의 화면이나 구현된 Agent 서비스가 아니다.

유지한 insight:

1. 추천할수록 후보가 늘어날 수 있다.
2. 고객에게 필요한 것은 더 많은 정보가 아니라 마지막 미확인 조건일 수 있다.
3. 가장 싼 구매와 가장 덜 낭비하는 구매는 다르다.
4. 상품을 사지 않게 만드는 답도 좋은 쇼핑 경험일 수 있다.
5. 고객은 상품보다 자신의 생활 과업을 해결하려 한다.

발산 조건: 단순 AI 요약·추천·계산만으로는 탈락. Agent가 조사·제거·협상·기다림·감시·되묻기 같은 일을 실제로 담당해야 한다. 쇼핑의 익숙한 문법을 하나 이상 뒤집고, 데모 한 장면으로 설명 가능해야 한다. 외부 전송·구매는 사용자 위임 범위 안에서만 실행하는 제품 구상이다. 이번 결과물은 그런 외부 행동을 실행하지 않는다.

## 1. 새로운 product interaction 12개

| 번호 | Interaction | Agent가 맡는 행동 | 한 장면으로 설명하는 Demo | 깨는 문법 |
|---|---|---|---|---|
| 01 | **상품 면접장** | 필수 조건을 질문으로 만들고 각 상품의 상세·문의·리뷰에서 근거를 찾는다. 답할 근거가 없으면 보류 | 높은 별점의 상품이 ‘이 질문에는 근거가 없습니다’라며 대기석으로 이동 | 고객이 비교한다 → 상품이 자격을 입증한다 |
| 02 | **쇼핑 퇴근** | 확인 질문을 전달하고 답변·조건 변화를 기다린다. 결정에 영향을 주는 변화만 보고 | ‘오늘 할 일은 끝났어요. 판매자 답변은 제가 기다릴게요.’ 상품 화면이 닫힘 | 고객을 붙잡는다 → Agent가 숙제를 넘겨받는다 |
| 03 | **결정권 위임장** | 필수 조건·예산·선호 규칙으로 후보를 제거하고 규칙 밖의 충돌만 되묻는다 | 18개 후보 대신 ‘위임 범위를 벗어난 질문 1개’가 남음 | 모든 결정을 고객이 내린다 → 예외만 결정한다 |
| 04 | **반품부터 시작하는 쇼핑** | 걱정하는 실패를 받아 상품 조건과 실패 부담을 조사하고 해소되지 않은 후보를 막는다 | ‘샀는데 둘 곳이 없다’를 선택하자 크기 미확인 상품이 후보에서 빠짐 | 장점부터 판다 → 후회 조건부터 없앤다 |
| 05 | **장바구니 파업** | 담는 이유를 확인하고 배송 문턱을 채우는 불필요한 물건과 중복품을 제거한다 | 배송비보다 비싼 추가품이 장바구니 밖으로 되돌아감 | 더 담도록 유도한다 → 덜 담도록 개입한다 |
| 06 | **미래의 내가 반려했습니다** | 소비량·재고·확인된 기한을 대조해 남을 가능성이 큰 구성을 제외한다 | 구매를 누르자 미래 달력에서 ‘이날에도 40봉이 남습니다’라는 반려 | 오늘 가격으로 결정한다 → 미래의 처리 가능성으로 결정한다 |
| 07 | **내 몫만 협상** | 필요한 수량에 맞는 기존 구성과 허용된 묶음 변경을 조사하고 판매자에게 제안한다 | 100봉에서 ‘내 몫 30봉’을 꺼내면 가능한 판매 구성을 확보하거나 협상 불가 표시 | 판매 단위를 받아들인다 → 필요한 단위로 거래를 요청한다 |
| 08 | **살림 리허설** | 과업을 단계로 나누고 보유품으로 수행 가능한지 검사한다. 막히는 단계만 구매 과제로 만든다 | 내일 아침을 재생하다 한 단계에서 멈추고 그때 처음 상품 등장 | 상품부터 고른다 → 생활을 먼저 실행한다 |
| 09 | **새 물건 입주심사** | 공간·규격·역할 중복을 확인하고 자리가 없거나 대체 관계가 불명확하면 보류한다 | 19종 세트가 작은 수납장 앞에서 ‘어느 물건을 대신하나요?’라고 묻는다 | 살 수 있으면 산다 → 생활에 들어갈 자격이 필요하다 |
| 10 | **쇼핑 종료 버튼** | 필수 조건과 남은 불확실성을 조사해 충분하면 추가 후보 노출을 멈춘다 | ‘이 정도면 됐어’를 누르면 추천 영역이 닫힘 | 추천을 계속한다 → 탐색을 종료한다 |
| 11 | **빈 장바구니 영수증** | 보유품이 목표를 충족하는지 조사해 불필요한 구매를 제거하고 과업 완료를 기록한다 | 상품 0개인데 ‘아침 준비 가능 / 추가 구매 없음’ 영수증 발급 | 결제해야 끝난다 → 과업이 해결되면 끝난다 |
| 12 | **딱 한 번만 물을게** | 가장 많은 불확실성을 없앨 질문을 고르고 답변에 따라 후보를 실제로 제거한다 | ‘인덕션인가요?’에 답하자 부적합 후보가 사라짐 | 고객이 검색 조건을 만든다 → Agent가 필요한 질문을 찾는다 |

12개 모두 연출을 지워도 대신 수행하는 일이 남아야 한다. 역할극·캐릭터·애니메이션만 있고 후보나 판단 상태가 변하지 않으면 탈락이다.

## 2. 더 기억에 남는 5개 선정

| 남긴 interaction | 남긴 이유 | 단독으로 약해질 수 있는 지점 |
|---|---|---|
| 상품 면접장 | 고객과 상품의 관계가 뒤집히고, 답할 수 없는 상품이 대기하는 상태가 선명하다 | 상품끼리 대화하는 연출만 있으면 비교표와 다르지 않다 |
| 쇼핑 퇴근 | 서비스가 고객에게 나가도 된다고 말한다. Agent의 가치가 고객이 없는 동안 발생한다 | 실제 대기·상태 갱신 없이 푸시만 보내면 일반 알림 기능이다 |
| 미래의 내가 반려했습니다 | 미래의 잔여 재고를 현재의 수정 행동으로 연결한다 | 계산값만 보여주고 실제 구성 교체를 못 하면 기존 다먹고샵과 같다 |
| 살림 리허설 | 생활 과업이 막히는 순간에만 상품이 등장한다 | 미리 정한 상품을 스토리로 포장하면 상황별 기획전으로 돌아간다 |
| 빈 장바구니 영수증 | 커머스의 빈 장바구니를 실패가 아니라 완료의 증거로 바꾼다 | 보유품 검증 없이 구매하지 말라고만 하면 근거 없는 선언이다 |

선정하지 않은 이유: 결정권 위임장과 딱 한 번의 질문은 유용한 내부 동작이지만 첫 장면의 독창성이 약하다. 반품 시작·입주심사는 다른 후보에 흡수 가능하다. 장바구니 파업은 절약 계산기, 내 몫 협상은 물류·판매 운영으로 무게중심이 옮겨갈 수 있다. 쇼핑 종료 버튼에는 무엇을 끝냈는지 보여주는 증거가 더 필요하다.

## 4. 최상위 Big Idea 3개

### 01 상품 오디션

> 고객님은 퇴근하세요. 상품들이 답할 차례입니다.

**고객 문제:** 후보를 고른 뒤에도 중요한 조건을 직접 확인하고, 미확인 답변을 기다리며 다시 방문해야 한다.

**근거:** 이전 탐색의 O09·O10·O11. 냄비 문의 2건이 제조국 확인에 관한 것이었고 현재 필수정보에 제조국이 표시됐다. 크기·재질 일부는 상세참조로 연결됐다. 이미 속성별 리뷰 요약이 있으므로 또 하나의 요약이 해결책은 아니다. 문의 당시의 정보 상태와 고객 나이는 알 수 없다.

**제품 interaction:** 고객이 포기할 수 없는 조건을 남김 → Agent가 후보별 근거 조사 → 불일치는 탈락, 미확인은 대기 → 사용자는 퇴근 → 답변이 오면 Agent가 판정 갱신 → 결과 또는 고객만 답할 수 있는 질문 하나가 돌아옴.

**화면:** 조건 칩, 후보별 심사 카드, 원문 근거, 대기 상태. 쇼핑 퇴근 뒤에는 상품 목록 대신 ‘남은 확인 1건’만 보인다. 답변이 와도 충족하지 못하면 최종 후보 0개가 가능하다.

**Agent의 실제 역할:** 조사·근거 대조·제거·확인 질문·대기·상태 갱신. 미확인을 적합으로 바꾸지 않는 것이 핵심이다.

**한 장면:** 세 후보 중 둘이 조건 불일치로 탈락하고 하나가 답변 대기. ‘지금은 고객님이 하실 일이 없습니다.’

**왜 GS:** 같은 상품에 연결된 필수정보·판매자 답변·리뷰·판매 구성을 활용할 수 있다. 실제 서비스에는 판매자 문의 연동과 비동기 작업 기반이 필요하다.

**HTML 데모:** 가상 조리도구 3개와 수납 폭·열원·가격 조건을 사용한다. 실제 냄비의 성능·치수라고 주장하지 않는다. 조사 실행 → 퇴근 → 가상 판매자 답변 18.5cm 또는 21cm 도착 → 적합 또는 최종 후보 없음까지 시연한다. 외부 문의나 감시는 실행하지 않는다.

### 02 미래반품

> 배송 전에, 남게 될 물건을 먼저 돌려보내세요.

**고객 문제:** 대용량의 낮은 단가가 실제 소비량과 맞지 않을 때 고객은 적정 구성과 낭비 위험을 따로 계산해야 한다.

**근거:** O13·O15·O18. 관찰 당시 견과 100봉 109,000원과 60봉 69,000원이 함께 노출됐다. 리뷰에는 소비 방식과 기간 평가가 달랐다. 현재 출고품의 소비기한은 확보하지 못했고, 두 구성의 상세 성분·혜택 동등성도 미검증이다.

**제품 interaction:** 구매 예정 구성을 선택 → 미래 달력에 소비될 양과 남을 양이 나타남 → 고객이 남을 부분을 덜어내기 → Agent가 실제로 판매되는 더 작은 구성으로 교체 → 미래 재고와 지출 갱신.

**화면:** 소비속도, 인원, 가정한 기간, 봉 수 단위 재고판. 남을 봉지는 다른 색과 라벨로 구분한다. 작은 구성이 없는 경우 ‘남는 수량만 잘라 판매’하지 않는다.

**Agent의 실제 역할:** 상품 단위·현재 재고·기한의 근거 확인, 구성 동등성 조사, 부적합 수량 제외, 가능한 판매 구성 탐색·교체. 산술은 계산 모듈이 담당한다.

**한 장면:** 혼자 주 5봉·가상 12주 조건에서 100봉 중 40봉이 남음 → ‘남을 40봉 덜어내기’ → 60봉 구성으로 교체.

**왜 GS:** 이미 존재하는 대용량과 대체 구성, 사용 맥락 리뷰를 연결할 수 있다. 출고 로트별 기한과 실제 구성 동등성 확인은 서비스화 전제다.

**HTML 데모:** 관찰 시 가격·수량을 참고하되 기간은 가상 12주다. 인원·주당 섭취량을 바꾸면 잔여량이 달라진다. 기간 미확인 모드에서는 잔여량 확정과 자동 구성 변경을 중단한다. 40,000원은 수령량도 다른 두 구성의 총지출 차이이며 순수 절약액으로 표시하지 않는다. 실제 반품·소분·장바구니 수정은 없다.

### 03 내일 재생

> 상품을 고르지 말고, 하고 싶은 하루를 실행하세요.

**고객 문제:** 생활용품 초보는 목표를 준비물로 바꾸고, 보유품으로 대체 가능한지 판단한 뒤 구매 목록을 만들어야 한다.

**근거:** O02·O03·O06. 상품군 카테고리와 ‘자취 냄비’ 441개 검색 결과는 목적·규격이 다른 상품을 제시했다. 실제 초보 고객의 어려움이나 과잉 구매를 측정한 것은 아니므로 세 후보 중 사용자 검증 필요성이 특히 크다.

**제품 interaction:** 하고 싶은 일을 고름 → 보유품·호환 조건 입력 → Agent가 작업 단계를 검사 → 가능한 단계는 통과 → 막히는 단계에서만 질문 또는 상품 등장 → 모두 충족되면 빈 장바구니 완료 영수증.

**화면:** 생활 과업 재생 버튼, 보유품 체크, 통과/확인 필요 단계, 부족 기능 하나, ‘추가 구매 0개’ 영수증. 상품 피드는 없다.

**Agent의 실제 역할:** 과업 분해·필요 기능 도출·보유품 대조·호환성 확인·중복 제거·막힌 지점만 되묻기. 단순 생활용품 추천 목록을 만들지 않는다.

**한 장면:** 전자레인지로 아침 한 끼 준비를 점검하다 적합한 식기 확인에서 멈춤 → ‘집에 있고 사용 가능 표시를 확인했어요’ → 모든 단계 통과 → ‘준비 완료 · 추가 구매 0개’.

**왜 GS:** 조리도구·식품·생활용품과 상품의 사용 조건을 연결할 수 있다. 과업별 조건표와 보유품의 검증 상태가 있어야 일반 준비물 챗봇과 달라진다.

**HTML 데모:** 사전 정의한 한 가지 과업과 가상 보유품으로 상태 변화만 시연한다. 조리법·가열 시간·식품 안전성을 검증하는 도구가 아니다. ‘전자레인지 사용 가능’ 같은 조건은 사용자가 표시를 확인했다고 명시적으로 입력한다.

## 5. 비교와 해석

- **상품 오디션:** Agent가 고객 대신 조사·대기한다는 역할이 가장 선명하다. 먼저 구현할 후보로 제안.
- **미래반품:** 미래 재고를 덜어내면 현재 구성이 바뀌는 한 장면이 가장 직관적이다.
- **내일 재생:** 커머스의 시작과 끝을 가장 크게 바꾼다. 실제 과업·입력 부담 검증이 중요하다.

이는 정성적 기획 판단이며 고객 실험 결과나 공식 평가 점수가 아니다. 세 개는 하나의 앱에 모두 합치는 기능 제안이 아니라 독립 후보다.
