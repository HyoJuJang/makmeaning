## 이 문서의 용도

메인 작업에서 기존 goal의 제품 목적·source of truth·상태 권한·완료 기준을 수정할 때 사용하는 독립 문서다. 기존 기획을 다시 발산하거나 다른 세션에서 구현을 시작하라는 요청이 아니다. 원래 goal은 [최종 기획 4-2](doc03_final_ideation.md#4-2-goal-원문)에 보존했고, 검토와 보완 원문은 같은 문서 4-3·4-4에도 추가했다.

이 문서는 goal을 수정하기 위한 입력이며, 현재 코드의 구현·검증 완료를 주장하지 않는다. 문서 작성만으로 메인 작업의 실행 goal이 변경되지는 않는다.


## 보완 /goal 원문

```text
/goal

GS SHOP에서 상품을 자신의 생활과 연결해 상상하기 어려워 ‘나를 위한 곳이 아니다’라고 느끼는 고객에게, 자신의 보유 상품과 생활 상황을 알아보고 그 맥락에서 다음 상품을 탐색하며 선택이 일관되게 남는 G:Scene mobile web prototype을 완성하고 배포하라. Room은 경험의 개인적인 입구이자 생활의 요약이고, 각 카테고리 씬은 해당 생활 영역을 자세히 탐색하고 선택하는 공간이다. 상품 동기화와 화면 이동만으로 완료하지 말고, ‘내 생활에서 새로운 쇼핑이 시작된다’는 연결을 실제 사용 흐름으로 보여라.

제품 방향은 docs/ideas/doc03_final_ideation.md의 문제와 아이디어를 따른다. 이 보완 goal은 기존 goal의 대칭적인 화면 일치 기준을 카테고리 기준의 데이터·표현·상태 계약으로 구체화한다. 이미 승인된 Next.js + TypeScript, 공통 상품 DB/API, 네 카테고리, 기존 Scene 탐색·추천·미리보기·찜·장바구니와 생활 interaction을 보존하고 필요한 연결만 수정한다. AGENTS.md와 crit01의 초기 DB/backend/category 제외 규칙은 이미 승인된 통합 범위에 적용하지 않는다. 새 전체 서비스, 실제 로그인·결제·고객 데이터·GS SHOP API·학습 기반 추천 모델, 불필요한 DB·MCP·game engine은 추가하지 않는다.

네 카테고리 모두 실제 상품 ID에 연결된 가상 사용자의 구매·보유 데이터와 확정된 생활 상태를 원본으로 삼는다. 이 데이터에서 공통 대표 상품 선정 규칙으로 category hero를 구성하고, Room은 그 결과 중 보유 조건에 맞는 상품과 확정 상태를 축약해 표현한다. Fashion wardrobe → Room wardrobe, Food fridge/pantry → Room fridge/pantry, Living scene → Room living area, Beauty vanity/shelf → Room vanity의 의미적 방향을 유지한다. hero 화면의 DOM·방문 여부·임시 필터·스크롤을 원본으로 삼지 않는다. Room의 기존 슬롯·그림에 맞추기 위해 카테고리 상품을 바꾸거나 누락하지 말고, Room 전용 가짜 구매 목록을 만들지 않는다.

상품 목록·hero·Room에 등장하는 같은 물건은 동일 product ID를 사용한다. Room이 모든 상품을 표시할 필요는 없으며, 대표 보유 상품을 작게 보여주되 현재 착장 등 확정된 핵심 상태가 표시 제한으로 누락되지 않게 한다. hero에 cart/preview를 보여줄 경우 보유 상품과 구분하고 Room에 이미 가진 물건처럼 옮기지 않는다. 배경 장식과 실제 보유 상품도 구분한다. stylized 표현은 가능하지만 양쪽에서 같은 상품임을 색·형태·이름 등으로 알아볼 수 있어야 한다. 일반화된 그림을 정확한 실상품 외형이나 가상 피팅으로 표현하지 않고, 확인하지 않은 상품 정보는 만들지 않는다.

보유 관계, 장바구니, 임시 미리보기, 확정 생활 상태, 식품 잔량을 구분하라. 현재 docs/design/outfit_food_contract.md의 계약에 따라 착장은 Fashion의 명시적 적용으로만 확정하며, Room에서는 해당 확정 착장을 반영한다. Room에서 이미 허용된 식품 소비 등은 동일 상품 ID의 공통 상태를 갱신하고 양쪽 화면에 반영한다. preview 취소·화면 이탈은 확정 상태를 덮어쓰지 않고, cart 추가를 구매로 처리하지 않는다. 그림을 공유하는 두 상품의 잔량도 각각 유지한다. Room의 배치·크기·장식 변경은 원본 상품·보유 데이터를 바꾸지 않는다. 확정 상태와 찜·장바구니는 새로고침·방 복귀 후 복원하고, 초기화는 개인 데모 상태만 되돌리며 공통 상품 DB는 변경하지 않는다.

공간의 첫 object 탭은 접근과 생활 interaction, 준비된 같은 object의 재탭은 올바른 카테고리 이동이라는 현재 계약을 유지한다. 연속 입력과 화면 왕복 뒤에도 동작이 안정적이어야 한다. 최소 한 대표 Fashion 또는 Living 시나리오에서는 보유 상품이나 선택한 생활 상황이 기존 탐색·추천의 맥락으로 이어지고, 다음 상품을 왜 보는지 화면에서 이해할 수 있게 하라. 단순히 카테고리 URL을 여는 것으로 이 조건을 통과시키지 않는다. 추천·미리보기·장바구니가 실제 구매 완료로 오인되지 않게 하고, 모든 카테고리에서 ‘내 공간’으로 돌아가는 경로를 이해할 수 있어야 한다.

먼저 진행 중인 작업과 최신 사용자 결정을 확인하고 기존 결과를 재사용하라. 카테고리 데이터와 대표 상품 선정 규칙을 먼저 검증한 뒤 hero와 Room을 연결하라. 구현 세부사항·작은 UX 선택·상품 샘플·테스트·병렬화는 자율적으로 결정하되, 제품 핵심 방향·큰 범위 확장·새 계정/인증/비용·민감정보 판단만 사용자에게 확인한다. 독립 작업만 필요에 따라 sub-agent에 위임하고 Main Agent가 계약·통합·전체 품질·Git·배포를 책임진다. 세부 계획과 결정·실패·검증 증거를 저장소에 남겨 다른 세션도 동일 기준으로 이어갈 수 있게 하라. 다른 작업의 승인된 범위와 진행을 임의로 지우거나 중단하지 않는다.

완료 검증은 현재 그림과 데이터가 우연히 맞는 상황을 넘어야 한다. 네 카테고리의 대표 상품 A를 B로 바꾸는 테스트에서 hero와 Room의 표시 규칙·ID가 함께 바뀌는지, 같은 그림을 쓰는 두 식품의 잔량이 독립적인지, cart/preview만으로 보유 물건이 생기지 않는지, 카테고리를 먼저 방문하지 않은 Room 직접 진입도 정확한지, Room의 시각적 배치 변경이 원본을 바꾸지 않는지 확인하라. 데이터 변경 검사는 격리된 fixture나 개인 데모 상태로 수행하고 공통 상품 DB는 수정하지 않는다. Fashion 착장 적용 → Room 복귀 → 새로고침, Food 소비 완료/취소/연속 입력, Beauty·Living 확정 상태와 preview 구분, 초기화도 재검증한다.

390×844와 320×568 실제 화면에서 네 영역의 첫 interaction → 재탭 카테고리 진입 → 같은 상품·상태 확인 → 방 복귀 → interaction 재실행과 대표 생활 기반 쇼핑 시나리오를 검토하라. ID는 같아도 같은 상품으로 알아보기 어렵거나, 화면을 옮기며 맥락·상태가 끊기거나, 주요 조작이 가려지면 완료가 아니다. 구현과 구분된 Critic 관점으로 자세·배치·정렬·navigation·tone을 확인하고, 영향이 큰 문제를 한 번에 최대 3~5개 골라 수정 → 동일 상태 재검토 → 관련 회귀검사를 최소 한 차례 수행하라. 내부 점수와 Agent의 PASS 선언은 실제 행동·상태·전후 화면 증거를 대신하지 못한다.

production build·typecheck·관련 회귀검사·현재 구매/상품/Scene API 계약과 위 핵심 사용자 시나리오가 실제 실행으로 PASS하고, 흐름 단절·상품/상태 불일치 등 critical issue와 사용을 방해하는 주요 품질 문제가 없어야 한다. 기존 승인 계정으로 GitHub main과 Vercel을 동일 release commit에 맞추고 공개 URL에서도 재검증한 뒤 종료하라. milestone마다 확인된 결과·남은 문제·다음 행동을 짧게 알리되 사소한 판단마다 승인을 기다리지 않는다. 최종 보고에는 URL·commit·카테고리별 hero/Room product ID 연결·수정 전후 증거·실제 검증 결과·한계를 포함한다. 이번 검증은 구매 이력이 있는 가상 사용자의 prototype 경험에 한정되며 신규 고객의 첫 구매·실제 공감·전환 효과를 검증했다고 주장하지 않는다.
```

## 검토 배경과 근거

### 검토 결론

카테고리를 기준으로 방을 구성하는 방향은 맞다. 다만 이를 goal의 중심 목적 자체로 삼으면 G:Scene이 ‘상품 데이터가 정확히 동기화되는 앱’으로 축소될 수 있다. 데이터의 방향은 제품의 본질을 지키는 규칙이고, 목표는 고객이 자신의 생활에서 새로운 쇼핑을 시작하게 만드는 것이다.

**Room은 고객 경험의 개인적인 입구이자 생활의 요약이고, 카테고리 씬은 해당 생활 영역을 자세히 탐색하고 선택하는 공간이다. 카테고리의 데이터가 기준이라는 사실과 Room이 경험의 중심이라는 사실은 함께 성립한다.**

### 기존 논리에서 보완할 여섯 가지 공백

1. **상품 일치와 생활 기반 쇼핑 사이의 연결.** 상품 ID·착장 저장·왕복 이동이 모두 맞아도 방이 상품 목록으로 가는 그림 메뉴에 머물 수 있다. 최소 한 대표 시나리오에서는 보유 상품 또는 선택한 생활 상황이 다음 탐색의 기준으로 이어지고, 고객이 상품을 보는 이유를 화면에서 이해할 수 있어야 한다. 새 추천 모델을 만들라는 뜻이 아니라 기존 기능으로 이 연결을 증명하라는 뜻이다.
2. **카테고리 데이터와 화면 상태의 구분.** 원본은 카테고리별 상품·사용자 상태와 대표 상품 선정 규칙이다. hero 화면의 DOM·임시 필터·스크롤 위치가 원본이 아니다. 카테고리를 먼저 방문하지 않아도 Room은 정확해야 하며, 단순 탐색이나 카드 클릭이 확정 생활 상태를 바꾸면 안 된다.
3. **동일 상품·표시 집합·시각적 표현의 구분.** 양쪽에 나타나는 상품의 ID는 같아야 하지만 hero의 cart/preview까지 Room의 보유 물건으로 복사하면 안 된다. Room은 공통 대표 상품 선택 결과 중 보유 조건을 만족하는 항목을 축약한다. 확정 착장 등 핵심 상태는 단순 표시 개수 제한 때문에 빠지지 않는다. 같은 ID에 전혀 다른 그림을 붙이는 것도 제품 경험에서는 실패다. 색·형태·이름 등으로 같은 상품을 알아볼 수 있어야 하며, stylized 그림을 정확한 실물 재현이라고 주장하지 않는다.
4. **데이터 원본과 행동 권한의 구분.** secondary mirror는 모든 행동이 금지된 읽기 전용 화면이라는 뜻이 아니다. 다만 어디서 어떤 상태를 확정하는지는 기존 승인 계약을 따른다. 현재 착장 계약은 Fashion의 명시적 적용만 허용한다. Room에서 허용된 식품 소비는 공통 상태를 갱신한다. 보유 관계, cart, 임시 preview, 확정 applied 상태, 잔량/consumed 상태는 하나의 배타적 enum처럼 다루지 않는다. 보유 상품을 미리 볼 수도 있고 보유 식품의 잔량이 0일 수도 있다.
5. **자체 점수와 완료 증거의 구분.** 여러 Critic과 100점 평가는 보조 수단이다. 동일한 잘못된 가정을 공유하면 모두 PASS할 수 있다. 대표 상품 교체, 같은 그림을 쓰는 상품별 잔량 분리, cart의 보유 오인 방지, Room 직접 진입, 방 배치 변경 시 원본 불변 같은 검사를 통해 틀린 구현을 걸러낸다. 자세·배치·상품 인지성은 동일 상태의 전후 화면으로 검토한다.
6. **고객 문제와 이번 데모 검증 범위의 구분.** 문제는 ‘나를 위한 곳이 아니다’라는 거리감이지만 이번 slice는 구매 이력이 있는 가상 사용자다. 구매 이후의 상품·생활 연결 경험을 검증하는 범위로 명시하고, 신규 고객의 첫 구매 유도와 실제 공감·전환 효과까지 입증했다고 말하지 않는다. 이 공백을 이유로 새 기능을 임의로 확장하지 않는다.

기존 goal의 ‘같은 상품·상태를 이어받는다’는 표현만으로는 방에 맞춰 카테고리를 바꾸는 구현도 허용된다. 아래 보완 goal은 제품 목적을 유지하면서 **카테고리 데이터 → 대표 생활 씬 → Room mirror**의 결정 방향과, 그 방향을 깨뜨리지 않는 행동·검증 기준을 명시한다.
