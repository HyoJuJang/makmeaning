# 실제 상품 추천

`feat/recommendation`은 네 카테고리에서 userid와 선택 상품을 기준으로 추천한다. 선택하면 그 상품 하나만 추천 기준으로 사용하며, 전체 구매·장바구니 이력은 중복 제외에 사용한다. Python 전처리와 TypeScript 함수로 동작하며 별도 모델 서버는 필요하지 않다. 식품 레시피·인분·상황 선택 시나리오는 복구하지 않는다.

## 실행과 전환

저장소 루트 `data/`에 아래 다섯 CSV를 두고 실행한다. Node.js 22.18 이상과 Python 3.10 이상이 필요하다. 추가 Python 패키지는 없다.

```sh
npm ci
npm run recommendations:prepare
npm run dev
```

`/recommendations`에서 카테고리를 고르면 실제 이력이 있는 예시 사용자의 추천을 검토한다. 예시 사용자의 원본 ID는 브라우저에 전달하지 않는다.

직접 검토할 때는 예시 사용자 선택을 해제하고 dump의 `userid`를 입력한 뒤 `추천 조회`를 누른다. 저장 ID는 검토 화면 전용이다. 빈 값으로 조회하면 저장된 사용자 설정을 지우고 신규 사용자 결과를 확인한다. 방 화면은 홈 API의 사용자와 실제 선택한 상품을 사용한다.

본/백업 전환·나란히 비교·방 화면 적용 UI는 제거했다. 화면은 mode를 보내지 않고 서버 기본값을 사용한다. `RECOMMENDATION_MODE=behavior`가 기본이며 `metadata`로 설정하고 서버를 재시작하면 독립 메타데이터 전략을 사용할 수 있다. API는 명시적인 mode 요청을 계속 지원한다. 이전 브라우저의 추천 모드 저장값은 읽지 않는다.

식품·뷰티 페이지의 별도 `식품 둘러보기`, `뷰티 둘러보기` 목록과 정렬 UI는 제거했다. 구매·장바구니 컬렉션, 선택 상품 추천, 기존 상세·찜·장바구니 관리는 유지한다.

기존 3000 포트를 다른 작업에서 사용한다면 다음과 같이 별도 실행한다.

```sh
npm run build
node node_modules/next/dist/bin/next start --hostname 127.0.0.1 --port 3001
```

추천 검토와 추천 패널은 공통 상품 DB 없이 동작한다. 기존 홈·구매 컬렉션에는 별도로 `DATABASE_URL` 설정이 필요하다. 연결 실패 시 해당 공간의 기존 오류 안내와 추천 패널이 함께 표시된다.

## 데이터 계약

| 파일 | 사용하는 컬럼 | 처리 |
| --- | --- | --- |
| product.csv | prd_id, view_name, cate1_nm, cate2_nm, cate3_nm, cate4_nm, brand_name, discprice, domain | 실제 dump 컬럼 그대로 사용. 상품 ID는 문자열, 가격은 0 이상의 정수 원 |
| user_item_view.csv | userid, prd_id, dt, dh | 클릭 횟수 |
| user_item_cart.csv | userid, prd_id, dt, dh | 과거 담기 횟수 |
| user_item_order.csv | userid, prd_id, dt, dh, ordernum, ordqty | 양의 주문 수량만 사용, ordernum + prd_id 중복 제거 |
| user_item_rating.csv | prd_id, dt, dh, rating | 상품·시간별 중복은 최대값, 전체 기간 합산 |

`domain`은 fashion/living/food/beauty, `dt`는 YYYYMMDD, `dh`는 YYYYMMDDHH다. rating은 개인 평가가 아닌 상품 인기도다. 클릭 로그의 다른 세션 식별자로 사용자를 추정하지 않는다. 익명 ID, 잘못된 날짜·가격·점수·수량, 카탈로그 밖 상품은 제외하고 집계 수치를 기록한다. 주문 수량은 유효성 확인에 사용하며 여러 개 구매했다고 행동 가중치를 수량만큼 곱하지 않는다.

상품 사진은 사용자가 제공한 `https://asset.m-gs.kr/prod/{prd_id}/1/550` 규칙으로 표시한다. 검토 화면과 네 카테고리의 추천 카드에 공통 적용하며, 지연 로딩하고 원본 비율을 유지한다. 이미지 로딩 실패 시 같은 크기의 안내 영역을 표시한다. CSV 컬럼을 추가하거나 원본 이미지를 저장하지 않는다.

옵션·사이즈·용량·성분·현재 재고는 입력 컬럼에 없으므로 생성하거나 추정하지 않는다. 상품명에 원래 들어 있는 단위 표기는 원문으로만 표시한다. 3일간 구매·담기 이력은 관심 근거이며 현재 보유나 현재 장바구니 전체를 의미하지 않는다.

## 두 추천 방식

| 단계 | 본 추천 behavior | 백업 metadata |
| --- | --- | --- |
| 기준 상품 | 선택 상품 하나만. 선택이 없으면 구매·담기 우선, 클릭 보조 | 선택 상품 하나만. 선택이 없으면 구매·담기 상품 |
| 주요 근거 | 다른 사용자들의 공통 관심 + 카테고리 연결 + 상품 인기도 | 카테고리 연결 규칙 + 같은 브랜드 우선 |
| 근거 부족 | 선택 상품의 카테고리 연결. 선택이 없을 때만 인기도 → 기본 상품 | 선택 상품의 카테고리 연결. 선택이 없을 때만 기본 상품 |
| 선택·이력 없음 | 같은 도메인의 인기 상품, 점수가 없으면 기본 상품 | 기본 분류를 돌아가며 상품 선택 |
| 공통 제외 | 구매·담기 이력의 상품, 선택한 상품, 결과 중복, 다른 도메인 | 동일 |

본 추천 전처리는 사용자·상품마다 주문 5 / 담기 3 / 클릭 1을 적용한다. 행동별 횟수는 3으로 제한하고 사용자·도메인당 상위 30개로 상품 간 공통 관심을 집계한다. 사용자별 벡터를 정규화한 뒤 상품 간 코사인 유사도에 `공통 사용자 수 / (공통 사용자 수 + 3)`을 곱한다. 공통 사용자가 2명 이상인 연결만 상품당 상위 30개 보관한다. 이는 함께 관심을 보인 근거이지 동시 구매나 인과 관계를 뜻하지 않는다.

상품 선택이 없는 조회는 구매·담기 상위 8개와 클릭 보조 최대 3개(구매·담기가 없으면 클릭 8개)의 연결 점수를 합산한다. 행동 75%, 메타데이터 관계 15%, 로그 정규화 인기도 10%로 정렬한다. 이 비율은 성능 최적화 전 초기값이다. 결과가 부족하면 각 백업 단계로 보충하며 서로 다른 출처의 점수를 한꺼번에 정렬하지 않는다.

`anchorProductId`가 있으면 **선택 상품 하나만** 기준으로 삼는다. 행동 후보에도 카테고리 연결 규칙 또는 같은 분류 조건을 요구한다. 공통 사용자가 있다는 이유만으로 다른 분류를 추천하지 않는다. 인기도·기본 목록으로 빈 자리를 채우지 않는다. 후보가 없거나 선택 상품이 추천 카탈로그에 없으면 안내와 빈 결과를 반환한다. 다른 구매·담기 상품은 제외에만 사용하며 다른 상품의 클릭·횟수·날짜로 순위를 바꾸지 않는다.

메타데이터 백업은 클릭·빈도·날짜·상품 간 유사도·인기도를 순위에 사용하지 않는다. 명시 선택이 없으면 구매·담기 상품 ID 순으로 최대 8개 기준 상품을 고른다. 명시 연결은 100점, 같은 cate1+cate2는 30점, 같은 cate1은 10점이며 유효한 동일 브랜드는 8점을 더한다. 동점은 상품 ID 순이다. 선택도 이력도 없으면 분류별 기본 목록을 사용한다.

## 연결 규칙 수정

`src/lib/recommendation/rules.ts`의 `metadataRules`에 도메인별 9개, 총 36개 연결이 있다. 경로는 cate1부터 정확히 일치하는 접두 경로다. 상품명 키워드로 카테고리를 추측하지 않는다.

| 도메인 | 대표 연결 |
| --- | --- |
| 패션 | 상의 → 하의·아우터, 신발 → 양말, 가방 → 지갑 |
| 리빙 | 소파 → 쿠션·러그·조명, 식탁 → 식기, 커피머신 → 머그 |
| 푸드 | 커피 → 과자·빵, 시리얼 → 우유·두유, 스파게티면 → 소스 |
| 뷰티 | 토너 → 세럼, 세럼 → 크림, 샴푸 → 트리트먼트 |

건강식품에는 식사·레시피 규칙을 만들지 않았다. 선택 상품의 전용 연결이 없으면 같은 분류 후보를 찾는다. 뷰티는 성분 궁합이나 피부 적합성을 주장하지 않는다. 패션은 카테고리에 남성/여성이 명시된 경우 반대 분류와의 메타데이터 연결을 막으며 사용자 성별은 추정하지 않는다.

`engine.ts`의 가중치와 `DEFAULT_CATEGORIES`로 본 추천 비율과 기본 분류 순서를 바꿀 수 있다. 규칙·가중치 수정 후 테스트와 검토 화면으로 확인한다.

## API와 파일 구성

```http
POST /api/recommendations
Content-Type: application/json

{"userId":"검토할 userid","domain":"beauty","mode":"behavior","limit":6}
```

`userId`를 생략하면 신규 사용자, 대신 `sample: "beauty"`를 넣으면 해당 도메인 예시다. 둘은 동시에 지정하지 않는다. `anchorProductId`는 선택 상품 하나로 추천 범위를 고정한다. `purchasedProductIds`, `cartProductIds`는 선택 시 중복 제외에 사용하고, 선택이 없으면 사용자 기준 상품에도 보충한다. 검토 화면의 저장 userid가 방의 선택 상품을 덮어쓰지 않는다.

응답에는 상품, 선정 이유, 출처, 기준 상품, 점수 구성, 자동 백업 이유, 집계 기간이 있다. 원본 userid는 응답에 없다. `GET /api/recommendations/status`는 준비 상태와 집계 수치를 제공한다. 잘못된 요청은 400, 추천 데이터가 준비되지 않았으면 POST는 503이다. 사용자별 응답은 `Cache-Control: no-store`다.

- `scripts/recommendation/prepare.py`: CSV 전처리. `--data-dir`, `--output-dir` 지원.
- `.recommendation/catalog.json`: 상품·인기도·상품 간 연결·집계. 서버에서 캐시한다.
- `.recommendation/users/00.json` ~ `ff.json`: SHA-256(userid) 앞 두 글자별 사용자 이력. 실제 사용자 키가 들어 있으므로 비공개 데이터다.
- `.recommendation/samples.json`: 검토용 예시 사용자 ID. 서버만 읽는다.
- `src/lib/recommendation/`: 순수 추천 함수, 규칙, 서버 저장소, 요청 검증.
- `src/components/recommendation/`: 공통 추천 카드·패널·검토 화면·설정.

원본 CSV와 생성 인덱스는 Git·public·Next 배포 추적 대상에서 제외한다. 생성 데이터는 서버 런타임에 별도 배치하고 필요하면 `RECOMMENDATION_DATA_DIR`로 경로를 지정한다. 현재 약 421MB인 사용자 인덱스를 Vercel 함수에 자동 포함시키지 않는다. 데이터 교체 후 전처리를 다시 실행하면 변경된 파일을 서버가 다시 읽는다.

## 검증과 남은 평가

```sh
npm run test:recommendations
npm run recommendations:check
npm run typecheck
npm run build
# production 서버 실행 후, 동일한 로컬 인덱스로 실제 userid 조회까지 확인
SMOKE_BASE_URL=http://127.0.0.1:3001 npm run test:recommendations:http
```

`recommendations:check`는 실제 데이터로 네 도메인의 두 방식, 제외·중복·신규 사용자를 검사한다. 비교용 예시는 연결 근거가 풍부한 사용자로 선정하므로 전체 사용자 품질을 대표하지 않는다. 현재 검증은 동작·데이터 정합성 검증이다. 별도 시간 분리 평가, 추천 적합성 사용자 검토, 클릭·구매 전환 평가는 아직 하지 않았다.

현재 API는 내부 검토용으로 요청의 userid를 신뢰한다. 공개 운영 시에는 인증된 세션에서 userid를 주입하는 접근 계약과 인덱스 저장 위치를 별도로 연결해야 한다. 추천 카드 조회·선택 상품 연결·근거 검토를 구현했으며 실제 주문·서버 장바구니 쓰기는 하지 않는다.

실행 데이터와 검수 결과는 [review.md](review.md)에 기록했다.
