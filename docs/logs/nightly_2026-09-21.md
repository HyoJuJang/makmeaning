============================================================
2. PRODUCT ESSENCE — 절대 잃지 말 것
============================================================

G:Scene이 해결하려는 핵심 문제:

GS SHOP에서 상품을 자신의 생활과 연결해 상상하기 어려워
"나를 위한 곳이 아니다"라고 느끼는 고객에게,

상품이 나열된 쇼핑몰이 아니라

"내가 구매한 물건들과 함께 살아가는 나의 공간"

에서 새로운 쇼핑을 시작하게 한다.

핵심 경험은:

방
→ 내가 가진 상품과 생활
→ 관심/상황에 따른 쇼핑
→ 다시 내 공간

으로 이어지는 하나의 loop다.

G:Scene은 단순한:

- 귀여운 방
- 게임
- 아바타 서비스
- UI 리디자인
- 상품 추천 화면

이 아니다.

쇼핑몰의 출발점을
"무엇을 팔 것인가"에서
"이 사람은 어떤 생활을 하고 있는가"로 바꾸는 것이 핵심이다.

3. SUCCESS CRITERIA
============================================================

오늘 밤 작업은 아래 네 가지를 모두 만족해야 성공이다.


### A. HUMAN-EYE QUALITY

기능적으로 정상이라는 것만으로는 부족하다.

사람이 화면을 봤을 때 즉시

"여기 뭔가 이상한데?"

라고 느끼는 디테일을 적극적으로 찾고 제거한다.

특히:

- 캐릭터 눈 / 얼굴 정렬
- 시선 방향
- 머리와 몸 비율
- 앉았을 때 골반 위치
- 다리 벌어짐
- 팔 / 다리 관통
- sofa / vanity sitting pose
- 캐릭터와 가구의 grounding
- 상품이 공중에 뜨는 문제
- 쿠션 / 패브릭의 이상한 placement
- 옷장의 옷 placement
- hanger / rail 정렬
- fridge 내부 상품 정렬
- lamp의 pivot / geometry
- wardrobe / fridge / window hinge
- object scale
- perspective
- z-index / occlusion
- 벽 / 바닥 / 가구 경계
- 버튼 / 아이콘 alignment
- active / inactive navigation 상태
- padding / spacing
- 텍스트 baseline
- 모바일 viewport clipping
- animation 중간의 기괴한 frame

을 실제 rendered 화면으로 확인한다.

"코드는 맞다"는 이유로 visual issue를 PASS하지 않는다.


### B. PRODUCT FLOW

최소한 아래 핵심 흐름이 실제로 작동해야 한다.

Room
→ object interaction
→ 준비 상태
→ 두 번째 interaction
→ category
→ 동일 사용자/상품 확인
→ room 복귀
→ interaction 재개

Fashion / Food / Living / Beauty의 연결이 깨지지 않는다.

새로고침 후 보존하기로 한 사용자 상태가 복원된다.

기존 기능을 polish 때문에 깨뜨리지 않는다.


### C. DEPLOYMENT

아침에 실제 URL을 열어 시연할 수 있어야 한다.

다음이 모두 확인되어야 한다.

- production build PASS
- typecheck PASS
- critical automated tests PASS
- API critical path PASS
- mobile critical flow PASS
- GitHub main과 deployment가 동일 release commit
- Vercel production URL 정상
- production 환경에서도 핵심 interaction PASS

local에서만 되는 상태는 완료가 아니다.

------------------------------------------------------------
TRACK A — PRODUCT POLISH / QA / RELEASE
------------------------------------------------------------

필요하면 다음 역할을 sub-agent로 분리한다.

### A1. Visual Critic

코드를 먼저 보지 않는다.

실제 rendered UI / screenshot을 먼저 본다.

역할:

"사람이 보면 이상한데 기능 테스트는 놓치는 문제"

를 찾는다.

문제를 좋게 설명하려 하지 않는다.

적극적으로:

- 기괴함
- 어색함
- 임시 구현 느낌
- AI 생성물 특유의 이상함
- alignment 문제
- 물리적으로 말이 안 되는 배치

를 찾는다.

한 round에서 가장 영향이 큰 issue 최대 5개만 선정한다.


### A2. Builder / Fixer

Visual Critic이 발견한 문제를 수정한다.

새로운 기능 추가는 최소화한다.

기존 architecture를 가능한 유지한다.

문제를 숨기거나 interaction을 제거해서 PASS시키지 않는다.


### A3. Functional / Regression QA

Visual fix 이후 기존 기능이 망가지지 않았는지 확인한다.

특히:

- 이동
- 옷장
- 냉장고
- sofa
- vanity
- window
- lamp
- category navigation
- 상태 복원
- mobile touch

를 확인한다.


### A Track Loop

run
→ canonical state 생성
→ screenshot / rendered UI inspect
→ visual defect 최대 5개 선정
→ fix
→ 동일 state 다시 inspect

"무엇을 더 보여줄까?"가 아니라
